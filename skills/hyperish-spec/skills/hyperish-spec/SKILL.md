# Hyperish 명세 스킬

빌드 에이전트가 하이퍼리쉬 코드를 작성하기 전에 제품 명세를 찾아 읽고 적용하기 위한 진입점이다.

## 명세 소스와 경로 해석

- 명세의 단일 원천: **https://github.com/hyperish/docs** (public).
- 이 스킬에 적힌 문서 경로(`docs/...`)는 **docs 저장소 루트 기준**이다. 이 스킬 파일의 위치(`skills/hyperish-spec/`) 기준 상대 경로가 아니다.
- 이 스킬이 docs 저장소 밖(예: hyper, ring, lace, hera 같은 코드 레포)에 설치된 경우, 명세는 `git clone https://github.com/hyperish/docs`로 받거나 raw URL(`https://raw.githubusercontent.com/hyperish/docs/<revision>/docs/00-vision.md` 형식)로 읽는다.
- 명세 내용을 다른 파일에 복사해 두지 않는다. 항상 원천 저장소에서 읽는다.

## 명세 revision 고정 (재현성)

- 작업을 시작할 때 명세의 **커밋 SHA를 기록**하고(예: `git -C docs rev-parse HEAD`, 또는 GitHub API로 main의 SHA 조회), 그 revision 기준으로 문서를 읽는다.
- 작업 결과물(PR 설명, 커밋 메시지 본문 등)에 **적용한 명세 revision을 남긴다.** 나중에 "당시 어떤 명세로 만들었는지"를 재현할 수 있어야 한다.
- main의 최신 변경을 맹목적으로 따라가지 않는다. revision 갱신은 작업 단위로 의식적으로 하고, 갱신으로 바뀐 상태(확정/제안/미정)를 다시 확인한다.

## 문서 상태 규칙 (가장 먼저 적용)

모든 문서와 절은 셋 중 하나의 상태를 가진다 (docs 저장소 README.md 참조).

- **확정**: 명시적으로 결정된 사실. 확정과 충돌하는 구조·코드를 작성하거나 제안하지 않는다. 바꾸려면 리뷰 승인과 새 결정 기록이 필요하다.
- **제안**: 따르되, 더 나은 대안이 있으면 근거와 함께 제시할 수 있다. 제안을 확정인 것처럼 단정해 후속 설계의 전제로 쌓지 않는다.
- **미정**: 임의로 정하지 않는다. `docs/11-open-questions.md`를 확인하고, 작업이 미정 사항에 걸리면 멈추고 리뷰어에게 확인을 요청한다.

## 확정 엔지니어링 방향 (2026-11-16 확정)

아래는 2026-11-16에 확정된 방향이다.

### 레포 구성

| 레포 | 역할 |
|---|---|
| hyper | 개발 프레임워크 |
| ring | 백엔드 |
| lace | 웹 |
| hera | 네이티브 |

### 구현 전략

- 코어는 대부분 **Rust**로 작성한다.
- 처음부터 전부 새로 만들지 않는다. **Rust proc macro로 DSL**을 만든다.
- 기존 라이브러리나 생태계 코어를 **포크한 뒤 unit optimization을 거치는** 방식으로 운영한다.
- **unit optimization의 구체적 의미·범위·도구는 아직 설명되지 않았다 (미정).** 최적화의 단위와 기준을 추측해 포크 운영 방식을 정하지 말고, 첫 적용 전에 확인한다.
- 포크는 **내부 운영 전략**이다. 외부 개발자에게 포크를 요구하는 기본 경로로 설계하지 않는다.

### 규약 모델 원칙

- 코어와 내부에서 쓰는 규약 모델은 **표준 준수보다 성능과 수직 통합 생산성이 극대화되는 스택**을 쓴다.
- **외부 호환은 개별 어댑터**로 해결한다. docs/07(HTTP/JSON)과 docs/08(WebSocket)은 **해당 어댑터를 채택하는 경우**의 제안 규약이며, 내부 코어 규약이나 유일한 외부 형식으로 굳어진 것이 아니다.
- 내부 규약의 구체 스택·포맷 선택은 미정이다. 특정 프로토콜·포맷을 확정된 것처럼 도입하지 않는다.

## 작업 범위 규칙

- 이 명세는 **프레임워크 패밀리 전 범위의 DX와 응용/개발 계층 기획**을 다룬다. 개별 제품의 화면·에디터 UX 기획은 이 명세의 범위가 아니다.
- ring·lace·hera의 세부 범위(예: ring과 Cloudflare 검토안의 관계, lace/hera의 정확한 역할 경계)는 미정 항목이 있다. 미정이 작업을 막으면 임의로 정하지 말고 멈추고 리뷰어에게 확인을 요청한다.

## 작업 절차

1. 명세 revision을 고정한다(위 "명세 revision 고정").
2. 작업 내용에 해당하는 문서를 위 표로 찾아 전문을 읽는다. 기억이나 요약에 의존하지 않는다.
3. 문서의 상태를 확인한다. 확정은 따르고, 미정은 임의로 정하지 않는다.
4. 구현이 명세의 제안과 다르게 가야 할 이유가 생기면, 코드를 바꾸기 전에 근거를 들어 제안하고 리뷰 승인을 받는다.
5. 명세에 없는 규격(숫자, 한도, 포맷)을 새로 정해야 하면 공식 문서 등 근거와 확인 날짜를 함께 남긴다 (docs 저장소 README 규칙).
6. 커밋은 `docs/09-development-rules.md`를 따른다: Conventional Commits, 한 커밋은 한 논리 변경. 문서 변경은 문서 단위로 커밋을 나눈다.

## 적용 예시

**작업**: ring에 새 조회 엔드포인트를 추가한다.

1. 명세 저장소의 main SHA를 기록해 revision을 고정한다.
2. `docs/03-ring-backend.md`를 읽어 이 엔드포인트가 ring의 책임(어댑터 서빙)에 맞는지, core와 adapter 중 어디에 놓이는지 정한다.
3. `docs/06-core-contracts.md`를 읽어 오류 분류(도메인/인프라), 취소 전파, 어댑터 변환·손실 규칙을 적용한다.
4. 외부 노출에 HTTP/JSON 어댑터를 쓰기로 했다면 `docs/07-api-protocol.md`의 응답 형식·에러 코드·버전닝을 따른다. WS 푸시가 필요하면 `docs/08-realtime-communication.md`도 읽는다.
5. 필드·경로 이름은 `docs/10-naming-conventions.md`, 브랜치·커밋은 `docs/09-development-rules.md`를 따른다.
6. 어느 단계든 미정 사항(예: ring의 저장소 백엔드 미확정)에 걸리면 임의로 정하지 않고 멈춰 확인한다.

## 하지 않는 것

- 제안·미정 내용을 확정인 것처럼 코드, 주석, 문서에 쓰지 않는다.
- 확정 사항과 충돌하는 리팩터링·구조 변경을 커밋하지 않는다.
- 명세 문서를 코드에 맞춰 임의로 수정하지 않는다. 문서 변경은 리뷰 승인 후 문서 단위 커밋으로 한다.
- unit optimization의 의미를 추측해 포크 운영 방식을 정하지 않는다.
- 내부 규약의 구체 스택·포맷을 확정된 것처럼 도입하지 않는다.
