# 01. DX 원칙

> 상태: **제안** (단, `hyper` 올인원 통합 워크플로 축·개발 생산성 중심의 표현 수단 개방성·컴포넌트 단위 조립과 아키텍처 고점 개방 원칙은 **확정**) · 기준일: 2026-11-18

하이퍼리쉬 프레임워크 패밀리의 DX(개발자 경험)를 설계하는 원칙입니다. API, DSL, 도구, 문서를 만들거나 트레이드오프를 판단할 때 이 순서대로 저울질합니다.

## 원칙 1. 첫 결과물까지의 시간이 가장 짧아야 한다 (왜 써야 하는지 즉시 체감)

- 새로 온 개발자가 **문서의 첫 코드 한 조각과 설치 한 줄만으로 "왜 이 스택을 써야 하는지, 기존 스택보다 생산성 체급이 얼마나 높은지"를 직관적으로 체감**하고 몇 분 안에 동작하는 결과를 보는 것을 첫 과제로 둡니다(문서 UX 레퍼런스: Dioxus 0.7 Learn/Welcome).
- **기존 Rust/Cargo가 Node.js라면 `hyper`는 Bun의 포지션**을 지향합니다. 파편화된 서드파티 도구·크레이트를 개발자가 일일이 조합하게 하지 않고, 프로젝트 초기화(`init`), 실시간 미리보기(`preview`), 정적 검사(`lint`), 테스트(`test`), 빌드(`build`), 그리고 기본 내장 코어(상태성 `signal`·직렬화·파서·Validation·API 스키마 계약)까지 `hyper` 하나로 즉시 동작하는 올인원(All-in-One) 경험을 제공합니다.
- 빈 프로젝트로 시작하지 않습니다. 문서를 따라 읽기만 하면 프로젝트 구조가 바로 이해되고 즉시 실행되는 스타터 템플릿과 예제가 기본 진입로입니다.

## 원칙 2. 구조를 제한하지 않고 개발자가 아키텍처를 직접 설계할 수 있게 고점을 높인다 (컴포넌트 조립성)

- 프레임워크가 고정된 폴더 구조(강제된 MVC 디렉터리 등)나 단일 아키텍처 패턴을 강요해 개발자의 손발을 묶지 않습니다. **바닥(진입장벽)은 낮추되, 천장(아키텍처 고점)은 극대화**합니다.
- 백엔드(`ring`)와 프론트엔드(`lace`, 웹·네이티브) 모두 **Rust 스타일의 컴포넌트(Component) 단위 설계**를 공통 조립 단위로 삼습니다:
  - 상태·의존성 주입(`provide`), 경계·미들웨어·가드(`wrap`), 라우트·핸들러·실시간 룸·뷰 트리를 **자기 완결적인 컴포넌트 단위**로 묶어 레고처럼 합성(`.mount()`)합니다.
  - 1인 개발자는 파일 하나에 컴포넌트를 간결하게 작성할 수 있고, 대규모 팀은 DDD·헥사고날·클린 아키텍처·MSA 등 원하는 아키텍처로 컴포넌트를 분할·조립할 수 있습니다.

## 원칙 3. DSL은 생산성을 위한 수단일 뿐, 더 효율적이면 어떤 방법이든 무관하다

- **DSL을 채택하는 이유는 오직 개발 생산성 때문**입니다([00-vision](00-vision.md)의 확정 방향). DSL 자체가 목적이 되어서는 안 됩니다.
- QML 기반 Slint 스타일이나 Dioxus `rsx!` 같은 proc macro DSL은 유력한 수단이지만, **GPUI처럼 순수 Rust 빌더·체이닝이나 코드젠 등 다른 방법이 생산성·가독성·효율성 면에서 충분하거나 더 낫다면 그 어떤 방법을 사용해도 무관**합니다.
- 어떤 표현 방식을 택하든 필요할 때 저수준 Rust 코드로 자연스럽게 내려갈 수 있어야 하며, **`lace`의 웹(DOM) 타깃과 네이티브(GPU/CPU) 타깃은 동일한 단일 UI 문법/표현 체계**를 공유합니다(웹 기능이 들어가느냐 네이티브 기능이 들어가느냐에 따라 타깃 확장만 분기).
- 구체적인 UI 표현 방식과 문법 세부는 [열린 결정](07-open-questions.md)에서 다룹니다.

## 원칙 4. 에러가 곧 문서다

- **컴파일 타임에 검증할 수 있는 종류의 오용**(타입·구조·스키마 위반)은 반드시 **컴파일 타임 진단 메시지**로 알립니다.
- I/O·외부 서비스·사용자 데이터처럼 **실행 시점에만 알 수 있는 실패**는 억지로 컴파일 타임으로 끌어올리지 않습니다. 런타임 오류로 정직하게 표면화하고 복구 방법을 함께 알립니다.
- 에러 메시지는 무엇이 틀렸는지와 어떻게 고치는지를 함께 말합니다. 진단 품질은 기능과 동급의 작업 항목입니다.

## 원칙 5. 확장은 포크 없이, 포크는 우리 내부 전략

- **성능 위주의 기존 라이브러리·프레임워크 포크 + unit optimization은 우리 내부의 코어 운영 전략**입니다. 수직 통합을 위해 모든 계층은 `hyper`의 core를 기준(ref)으로 삼아 구현하고, 그 위에 호환 어댑터를 둡니다. 외부 개발자에게 포크를 요구하지 않습니다.
- 외부 개발자의 기본 확장 경로는 **포크 없이 쓰는 확장 지점**(컴포넌트 조립, DSL 확장, 어댑터 인터페이스)입니다. 어댑터의 공통 계약은 [02-core-contracts](02-core-contracts.md) §5입니다.
- 내부 포크 절차는 문서화된 경로여야 하고([05-development-rules](05-development-rules.md) §7), 내부 전용 지식에 의존하지 않습니다.

## 원칙 6. 레지스트리 배포와 버전 신뢰

- SDK·도구는 레지스트리에 올려 설치하는 것을 기본으로 합니다. 소스를 받아 빌드해야 쓸 수 있는 상태를 기본으로 두지 않습니다.
- 버전은 [개발 규칙](05-development-rules.md)의 SemVer를 따르고, 하위호환을 깨는 변경은 MAJOR와 마이그레이션 안내를 함께 냅니다.

## 원칙이 충돌할 때

- 진입의 쉬움(원칙 1)과 아키텍처 고점·표현력(원칙 2·3)이 충돌하면, 첫 동선을 해치지 않는 선에서 기본값을 단순하게 두고 고급 조립 API를 하위 계층으로 열어 둡니다. 기능을 없애거나 구조를 강제하지 말고 기본 경로에서 단계적으로 드러냅니다.
- 내부 구현 편의와 개발자 경험이 충돌하면 개발자 경험이 우선입니다.
