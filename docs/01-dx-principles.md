# 01. DX 원칙

> 상태: **제안** (단, 올인원 통합 워크플로·컴포넌트 조립을 통한 아키텍처 고점 개방·생산성 중심 표현 수단 개방성은 **확정**) · 기준일: 2026-11-18

하이퍼리쉬 프레임워크 패밀리의 DX(개발자 경험)를 설계하는 원칙입니다. API, DSL, 도구, 문서를 만들거나 트레이드오프를 판단할 때 이 순서대로 저울질합니다.

## 원칙 1. 첫 결과물까지의 시간이 가장 짧아야 한다

- 새로 온 개발자가 **문서의 첫 코드 한 조각과 설치 한 줄만으로 "왜 이 스택을 써야 하는지, 다른 스택 대비 무엇이 좋은지"를 직관적으로 체감**하고 몇 분 안에 동작하는 결과를 보는 것을 첫 과제로 둡니다(문서 UX 레퍼런스: Dioxus 0.7 Welcome).
- 파편화된 서드파티 도구·크레이트를 개발자가 일일이 조합하게 하지 않고, 초기화(`init`)·미리보기(`preview`)·검사(`lint`)·테스트(`test`)·빌드(`build`)와 기본 코어 모듈이 하나로 준비된 올인원 경험을 기본 진입로로 둡니다.

## 원칙 2. 구조를 제한하지 않고 개발자가 아키텍처를 직접 설계할 수 있게 고점을 높인다

- 프레임워크가 고정된 폴더 구조나 단일 아키텍처 패턴을 강제하지 않습니다. **바닥(진입장벽)은 낮추되, 천장(아키텍처 고점)은 극대화**합니다.
- 상태·의존성 주입(`provide`), 경계·가드(`wrap`), 기능·뷰·라우트를 **자기 완결적인 컴포넌트(Component) 단위**로 묶어 합성할 수 있게 하여, 단일 파일 구성부터 대규모 아키텍처 분리까지 개발자가 직접 구조를 설계할 수 있게 합니다.

## 원칙 3. DSL은 생산성을 위한 수단이며, 영역별로 표현 방식을 명확히 고정한다

- **DSL을 채택하는 이유는 오직 개발 생산성 때문**입니다([00-vision](00-vision.md)). 같은 영역에서 여러 작성 방식을 중복 허용해 혼란을 주는 대신, 각 영역에 가장 생산적인 방식을 하나로 고정합니다:
  - **UI 뷰(화면 트리) 마크업 (`lace`)**: 깊은 중첩 가독성, 컴파일 타임 정적 템플릿 분리, 즉시 핫리로드를 위해 **proc macro DSL(QML/Slint · Dioxus `rsx!` 레퍼런스)로 고정**합니다.
  - **컴포넌트·라우트·미들웨어 조립 (`ring`, `lace`) 및 저수준 커스텀 드로잉**: 순수 **Rust 메서드 체이닝과 함수**로 고정합니다.
- 매크로 내부 표현식은 표준 Rust와 자연스럽게 결합되어야 하며, 저수준 시스템·렌더링 API로의 탈출구는 항상 열어 둡니다.

## 원칙 4. 에러가 곧 문서다

- **컴파일 타임에 검증할 수 있는 종류의 오용**(타입·구조·스키마 위반)은 반드시 **컴파일 타임 진단 메시지**로 알립니다.
- I/O·외부 서비스·사용자 데이터처럼 **실행 시점에만 알 수 있는 실패**는 런타임 오류로 정직하게 표면화하고 복구 방법을 함께 알립니다.
- 에러 메시지는 무엇이 틀렸는지와 어떻게 고치는지를 함께 말합니다.

## 원칙 5. 확장은 포크 없이, 포크는 우리 내부 전략

- 외부 개발자의 기본 확장 경로는 **포크 없이 쓰는 확장 지점**(컴포넌트 조립, DSL 확장, 어댑터 인터페이스)입니다([02-core-contracts](02-core-contracts.md) §5).
- 기존 라이브러리 포크 + `unit optimization`은 내부 코어 운영 전략이며([05-development-rules](05-development-rules.md) §7), 외부 개발자에게 포크를 요구하지 않습니다.

## 원칙 6. 레지스트리 배포와 버전 신뢰

- SDK·도구는 레지스트리에 올려 설치하는 것을 기본으로 하며, 버전은 [05-development-rules](05-development-rules.md) §5의 SemVer를 따릅니다.

## 원칙이 충돌할 때

- 진입의 쉬움(원칙 1)과 아키텍처 고점·표현력(원칙 2·3)이 충돌하면, 기본값을 단순하게 두고 고급 조립 API를 하위 계층으로 열어 둡니다. 기능을 없애거나 구조를 강제하지 않습니다.
- 내부 구현 편의와 개발자 경험이 충돌하면 개발자 경험이 우선입니다.
