# 01. DX 원칙

> 상태: **제안** (단, Dioxus `rsx!`·매크로 레퍼런스 및 `hyper` 통합 워크플로 축은 **확정**) · 기준일: 2026-11-17

하이퍼리쉬 프레임워크 패밀리의 DX(개발자 경험)를 설계하는 원칙입니다. API, DSL, 도구, 문서를 만들거나 트레이드오프를 판단할 때 이 순서대로 저울질합니다.

## 원칙 1. 첫 결과물까지의 시간이 가장 짧아야 한다

- 새로 온 개발자가 **설치 한 줄과 템플릿 하나로 몇 분 안에 동작하는 결과**를 보는 것을 첫 과제로 둡니다.
- **기존 Rust/Cargo가 Node.js라면 `hyper`는 Bun의 포지션**을 지향합니다. 파편화된 서드파티 도구·크레이트를 개발자가 일일이 조합하게 하지 않고, 프로젝트 초기화(`init`), 실시간 미리보기(`preview`), 정적 검사(`lint`), 테스트(`test`), 그리고 기본 내장 코어(상태성·직렬화·파서·API 계약)까지 `hyper` 하나로 즉시 동작하는 올인원(All-in-One) 경험을 제공합니다.
- 빈 프로젝트로 시작하지 않습니다. 스타터 템플릿과 예제가 기본 진입로입니다.
- 깊은 기능은 숨기지 않되, 첫 동선 위에 올라타지 않게 배치합니다.

## 원칙 2. 선언적 DSL(QML/Slint·Dioxus)과 가독성 높은 순수 Rust(GPUI)의 조화

- 개발자가 주로 쓰는 표현은 **QML 기반 Slint 스타일 및 Dioxus `rsx!` 감각의 proc macro DSL**입니다([00-vision](00-vision.md)의 확정 방향).
- 단, **GPUI처럼 DSL 없이 순수 Rust 빌더·체이닝만으로도 가독성이 충분한 경우에는 굳이 DSL을 쓰지 않아도 됩니다.** DSL과 순수 Rust 빌더 API를 1:1로 대응시켜, 상황에 따라 더 잘 읽히는 쪽을 고르거나 자연스럽게 내려갈 수 있어야 합니다. DSL이 감옥이 되면 안 됩니다.
- **웹(`lace`)과 네이티브(`hera`)는 동일한 UI 문법을 공유**합니다. 기본 UI 트리·상태 바인딩·프로퍼티 문법은 하나로 통일하고, 웹(DOM) 전용 기능이 들어가느냐 네이티브 전용 기능이 들어가느냐에 따라 타깃별 확장만 나뉘게 합니다.
- DSL의 세부 키워드·토큰 문법은 [열린 결정](07-open-questions.md)에서 다룹니다.

## 원칙 3. 에러가 곧 문서다

- **컴파일 타임에 검증할 수 있는 종류의 오용**(타입·구조·스키마 위반)은 반드시 **컴파일 타임 진단 메시지**로 알립니다.
- I/O·외부 서비스·사용자 데이터처럼 **실행 시점에만 알 수 있는 실패**는 억지로 컴파일 타임으로 끌어올리지 않습니다. 런타임 오류로 정직하게 표면화하고 복구 방법을 함께 알립니다.
- 에러 메시지는 무엇이 틀렸는지와 어떻게 고치는지를 함께 말합니다. 진단 품질은 기능과 동급의 작업 항목입니다.

## 원칙 4. 확장은 포크 없이, 포크는 우리 내부 전략

- **성능 위주의 기존 라이브러리·프레임워크 포크 + unit optimization은 우리 내부의 코어 운영 전략**입니다. 수직 통합을 위해 모든 계층은 `hyper`의 core를 기준(ref)으로 삼아 구현하고, 그 위에 호환 어댑터를 둡니다. 외부 개발자에게 포크를 요구하지 않습니다.
- 외부 개발자의 기본 확장 경로는 **포크 없이 쓰는 확장 지점**(DSL 확장, 어댑터 인터페이스)입니다. 어댑터의 공통 계약은 [02-core-contracts](02-core-contracts.md) §5입니다.
- 내부 포크 절차는 문서화된 경로여야 하고([05-development-rules](05-development-rules.md) §7), 내부 전용 지식에 의존하지 않습니다.

## 원칙 5. 레지스트리 배포와 버전 신뢰

- SDK·도구는 레지스트리에 올려 설치하는 것을 기본으로 합니다. 소스를 받아 빌드해야 쓸 수 있는 상태를 기본으로 두지 않습니다.
- 버전은 [개발 규칙](05-development-rules.md)의 SemVer를 따르고, 하위호환을 깨는 변경은 MAJOR와 마이그레이션 안내를 함께 냅니다.

## 원칙이 충돌할 때

- 진입의 쉬움(원칙 1)과 표현력(원칙 2)이 충돌하면, 첫 동선을 해치지 않는 선에서 표현력을 뒤로 뺍니다. 기능을 없애지 말고 기본 경로에서 내립니다.
- 내부 구현 편의와 개발자 경험이 충돌하면 개발자 경험이 우선입니다.
