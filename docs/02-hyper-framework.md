# 02. hyper: 개발 프레임워크

> 상태: 레포 역할과 전략 축은 **확정**(2026-11-16), 구조·절차는 **제안** · 기준일: 2026-11-16

hyper는 하이퍼리쉬의 개발 프레임워크 레포입니다([00-vision](00-vision.md)). 모든 레이어가 공유하는 공통 계약은 [06-core-contracts](06-core-contracts.md)를 따릅니다.

## 확정된 축

- 코어는 대부분 **Rust**로 작성합니다.
- **Rust proc macro로 DSL**을 만듭니다. 처음부터 전부 새로 깎지 않습니다.
- 기존 라이브러리나 생태계 코어를 **포크한 뒤 unit optimization**을 거칩니다. unit optimization의 구체적 의미는 미정입니다([열린 결정](11-open-questions.md)).
- 코어와 내부 규약 모델은 **표준보다 성능과 수직 통합 생산성이 극대화되는 스택**을 쓰고, 외부 호환은 **개별 어댑터**로 해결합니다([00-vision](00-vision.md)의 규약 모델 원칙). 구체 스택 선택은 미정입니다.

## 계층 책임과 의존 방향 (제안)

- hyper는 **도메인 모델과 DSL, 런타임 코어**를 소유합니다.
- 의존 방향은 한쪽입니다: **lace(웹)·hera(네이티브)가 hyper에 의존**하고, hyper는 어느 타깃 레이어도 알지 못합니다. ring(백엔드)과는 어댑터 경계([06-core-contracts](06-core-contracts.md) §5)로만 만납니다.
- hyper 안에 타깃 전용 코드(웹 전용, 특정 OS 전용)를 넣지 않습니다. 타깃별 코드는 각 레이어 레포로 갑니다.

## 구조 (제안)

```
hyper/
  crates/
    hyper/          # 사용자가 의존하는 진입 크레이트 (재수출과 안정 API)
    hyper-macros/   # proc macro DSL 구현
    hyper-core/     # 런타임 코어 (Rust)
  forks/            # 포크해 운영하는 외부 코어들 (아래 절차 참조)
  examples/         # 스타터 예제 (DX 원칙 1)
```

- 사용자는 `hyper` 크레이트 하나만 의존하고, 매크로와 코어는 재수출로 노출합니다.
- DSL 문법과 표현 범위는 미정이며, 정해지면 별도 문서로 분리합니다.

## 확장 지점 (제안)

외부 개발자의 기본 확장 경로는 **포크가 아니라 확장 지점**입니다([DX 원칙](01-dx-principles.md) 원칙 4).

1. **DSL 확장**: 새 매크로·속성 추가. 진입 크레이트를 통해 노출.
2. **어댑터 구현**: 외부 규약과 코어를 잇는 어댑터 인터페이스를 구현. 변환·손실·버전·비용 계약은 [06-core-contracts](06-core-contracts.md) §5.
3. **포크 코어 교체**: 우리 내부 운영 전략. 외부 개발자에게 요구하는 경로가 아닙니다.

## 빌드·테스트·진단 흐름 (제안)

- **빌드**: cargo workspace로 크레이트를 묶고, 사용자는 진입 크레이트만 의존합니다.
- **테스트**:
  - 코어 모델: 단위 테스트.
  - DSL: 매크로 전개 결과를 검사하는 테스트(전개 스냅샷)와, 잘못된 사용이 **컴파일 오류로 진단되는지** 검증하는 테스트(진단 메시지 스냅샷)를 둡니다. 진단 테스트용 도구 채택은 미정입니다.
  - 어댑터 경계: [06-core-contracts](06-core-contracts.md) §5의 변환·손실 규칙을 검증하는 계약 테스트.
- **진단**: 매크로 전개 결과는 `cargo expand`로 확인 가능한 상태를 유지합니다. 진단 메시지 품질(무엇이 틀렸는지 + 어떻게 고치는지)은 리뷰 항목입니다.

## DSL 설계 방향 (제안)

- 선언적 표현을 기본으로 하고, **컴파일 타임에 검증 가능한 것**(타입·구조·스키마)은 컴파일 타임에 검증합니다([DX 원칙](01-dx-principles.md) 원칙 2·3).
- DSL에서 못 하는 일은 Rust 코드로 자연스럽게 내려가는 탈출구를 둡니다.

## 포크 운영 절차 (제안, 최적화 세부는 미정)

기존 라이브러리·생태계 코어를 포크해 쓸 때 따르는 **내부** 골격입니다.

1. **선정**: 포크 대상을 정하고 라이선스를 확인해 기록합니다.
2. **격리**: 포크는 `forks/` 아래에 두고, 업스트림 원본과 우리 변경을 분리해 추적합니다.
3. **동기화**: 업스트림 업데이트를 가져오는 주기와 충돌 처리 방식을 정합니다.
4. **최적화**: unit optimization을 거칩니다. **최적화의 단위·기준·도구는 아직 정해지지 않았으므로(미정), 첫 적용 전에 확인합니다.**
5. **검증**: 포크본이 원본과 어떻게 달라졌는지(동작·성능) 비교 결과를 남깁니다.

## 배포 (제안)

- crates.io 계열 레지스트리에 SDK로 배포합니다([00-vision](00-vision.md)의 레지스트리 방향).
- SemVer와 CHANGELOG는 [개발 규칙](09-development-rules.md)을 따릅니다.
- 네이밍은 [네이밍·코딩 컨벤션](10-naming-conventions.md)의 Rust 절을 따릅니다.
