# 00. 방향

> 기준일: 2026-11-18

## 이 명세의 범위

- 이 문서 세트는 하이퍼리쉬 프레임워크 패밀리 **전 범위를 범용적으로** 다룹니다. 중심은 **DX(개발자 경험)와 응용/개발 계층**입니다.
- 범용이란 제품별 사례를 모아 두는 것이 아니라, **모든 제품과 코드 레포가 공유하는 추상 계약**을 뜻합니다.
- 개별 제품의 기획·화면·UX와 개별 코드 레포의 도메인·레퍼런스·내부 구조 세부는 각 제품과 각 코드 레포의 문서(`docs/00-overview.md` ~ `04-open-questions.md`)가 다룹니다.

## 코드 레포 (탐색용 역할표, 2026-11-18 확정)

| 레포 | 역할 |
|---|---|
| **hyper** | 올인원 개발 프레임워크 & 툴체인 (범용 코어 모듈 + CLI) |
| **ring** | 백엔드 프레임워크 |
| **lace** | 크로스플랫폼 UI 프레임워크 (Web DOM & Native GPU/CPU) |

이 표는 어떤 레포가 있는지 찾기 위한 최소 정보입니다. 각 레포의 세부 범위와 레퍼런스는 해당 레포의 `docs/00-overview.md`를 봅니다.

## 확정 엔지니어링 방향 (2026-11-18)

### 구현 전략

- 코어는 대부분 **Rust**로 작성하며, Rust 코드 레포는 개별 레포 단위로 `apps/`, `crates/` 모노레포([05-development-rules](05-development-rules.md) §1)로 운영합니다.
- 처음부터 전부 새로 만들지 않습니다. 성능 위주의 검증된 라이브러리·프레임워크를 **포크하거나 기반으로 삼아 `unit optimization`**([05-development-rules](05-development-rules.md) §7)을 거칩니다.
- 수직 통합을 위해 **`hyper`의 코어를 단일 기준(`ref`)으로 삼아 구현**하고, **그 위에 외부·타깃 호환 어댑터를 두는 구조**([02-core-contracts](02-core-contracts.md))로 작업합니다.
- **DSL 채택 이유는 오직 개발 생산성 때문**입니다. 생산성과 가독성이 충족되거나 더 효율적인 방법이 있다면 어떤 방법을 사용해도 무관합니다([01-dx-principles](01-dx-principles.md)).

### 규약 모델 원칙

- 코어와 내부에서 사용하는 규약 모델은 **표준 준수보다 성능과 수직 통합 시 생산성이 극대화되는 스택**을 씁니다.
- **외부 호환은 개별 어댑터를 구축**하는 방식으로 해결합니다. 내부 규약을 외부 표준에 맞추느라 성능·생산성을 포기하지 않습니다.
- 구체적인 내부 포맷·스택 선택은 [07-open-questions](07-open-questions.md)에서 추적합니다.
