# 00. 비전과 방향

> 기준일: 2026-11-16 (2026-11-16 전범위 범용 구조로 개정)

## 확정: 비전

### 하이퍼리쉬와 제품군

- 하이퍼리쉬는 크리에이티브 툴 패밀리입니다.
- 첫 제품은 three.js, wgpu, bevy 계열의 **리얼리스틱 그래픽 엔진**입니다. 시뮬레이션 성능과 결과물 퀄리티는 C4D급을 목표로 하고, Unreal이 필요 없는 대안을 지향합니다. 사용층은 **개발자, 디자이너, 필름 디렉터(연출자)**를 모두 아우릅니다.
- 이후 벡터 편집, 셰이더 편집, 사진 편집 툴로 확장합니다(Rive·Illustrator·Photoshop이 하는 영역).
- 엔진은 **오픈소스**로 공개하고, **레지스트리에 올려 SDK로 설치**해 쓸 수 있게 합니다.
- 생태계 목표는 직접 작품을 만드는 계획이 아니라, **다른 사람들이 이 엔진으로 만든 데모와 작품이 많이 나오는 상태**입니다.

### 레포 구성 (2026-11-16 확정)

| 레포 | 역할 |
|---|---|
| **hyper** | 개발 프레임워크 |
| **ring** | 백엔드 |
| **lace** | 웹 |
| **hera** | 네이티브 |

### 구현 전략 (2026-11-16 확정)

- 코어는 대부분 **Rust**로 작성합니다.
- 처음부터 전부 새로 만들지 않습니다. **Rust proc macro로 DSL**을 만듭니다.
- 기존 라이브러리나 생태계 코어를 **포크한 뒤 unit optimization을 거치는** 방식으로 운영합니다.
- unit optimization의 구체적 의미·범위·도구는 아직 설명되지 않았습니다(**미정**, [열린 결정](11-open-questions.md)).

### 규약 모델 원칙 (2026-11-16 확정)

- 코어와 내부에서 사용하는 규약 모델은 **표준 준수보다 성능과 수직 통합 시 생산성이 극대화되는 스택**을 씁니다.
- **외부 호환은 개별 어댑터를 구축**하는 방식으로 해결합니다. 내부 규약을 외부 표준에 맞추느라 성능·생산성을 포기하지 않습니다.
- 구체적인 내부 포맷·스택 선택은 아직 결정되지 않았습니다(**미정**, [열린 결정](11-open-questions.md)). 이 원칙은 선택 기준이며 특정 스택의 승인이 아닙니다.

## 이 문서 세트의 범위 (2026-11-16 개정)

- 이 문서들은 특정 제품 하나가 아니라 **프레임워크 패밀리 전 범위를 범용적으로** 다룹니다.
- 계획의 중심은 **DX(개발자 경험)와 응용/개발 계층**입니다. 에디터 UX 같은 개별 제품의 화면 기획은 여기서 다루지 않고, 제품별 문서가 생길 때 그곳에서 다룹니다.
- 제품군(그래픽 엔진과 이후 편집 툴들)은 이 프레임워크 위의 **응용**으로 위치시킵니다.

## 제안: 비전에서 파생된 방향

- hyper의 DSL이 개발자가 하이퍼리쉬를 만나는 첫 접점이 되게 합니다 → [01-dx-principles](01-dx-principles.md), [02-hyper-framework](02-hyper-framework.md)
- ring이 백엔드 규격([06](07-api-protocol.md), [07](08-realtime-communication.md))의 구현 주체가 되는 구조 → [03-ring-backend](03-ring-backend.md)
- 웹과 네이티브는 각각 lace, hera가 담당하고, 공통 규약(네이밍, 개발 규칙)을 공유합니다 → [04](04-lace-web.md), [05](05-hera-native.md), [09](09-development-rules.md), [10](10-naming-conventions.md)

## 미정

전체 목록은 [11-open-questions](11-open-questions.md)에서 추적합니다. 큰 것만 적으면:

- unit optimization의 정의와 운영 방식
- ring의 구현 범위와 기존 Cloudflare 중심 인프라 검토안의 관계
- lace·hera의 타깃 범위(웹 우선 여부, 네이티브 플랫폼)
- DSL의 구체 문법과 표현 범위

## 이 문서의 역할

이 문서는 "왜 만드는가"와 확정된 방향만 다룹니다. 각 레포와 규격의 세부는 각 문서에서 **제안** 상태로 다루며, 여기 적힌 확정 사항과 제안이 충돌하면 확정 사항이 우선합니다.
