# 00. 방향

> 기준일: 2026-11-18

## 이 명세의 범위

- 이 문서 세트는 하이퍼리쉬 프레임워크 패밀리 **전 범위를 범용적으로** 다룹니다. 중심은 **DX(개발자 경험)와 응용/개발 계층**입니다.
- 범용이란 제품별 사례를 모아 두는 것이 아니라, **모든 제품이 공유하는 추상 계약**을 뜻합니다.
- 제품은 이 프레임워크 위의 **응용**입니다. 개별 제품의 기획·화면·UX와, 개별 코드 레포의 구조·책임·구현 세부는 이 명세의 범위가 아닙니다. 각 제품과 각 코드 레포의 문서가 다룹니다.

## 코드 레포 (탐색용 역할표, 2026-11-18 확정)

| 레포 | 역할 | 주요 범위 및 레퍼런스 |
|---|---|---|
| **hyper** | 올인원 개발 프레임워크 & 툴체인 | **Rust/Cargo 생태계에 대한 Bun 포지션.** 웹·서버에 국한되지 않는 범용 개발 플랫폼으로, 프로젝트 `init`·`preview`·`lint`·`test`·`build` 등 개발 환경·생산성 올인원 통합, 상태성(`signal`)·직렬화·파서·공용 Validation·스키마·공통 UI 문법·규격 인터페이스 등 기본 내장(batteries-included) 범용 코어 모듈 보유 (레퍼런스: **Bun**, **Dioxus**, **QML/Slint**, **GPUI**) |

이 표는 어떤 레포가 있는지 찾기 위한 공통 기준입니다. 각 레포의 세부 설계는 해당 코드 레포의 `docs/`에서 동일한 문서 구조(`00-overview` ~ `04-open-questions`)로 다룹니다.

## 확정 엔지니어링 방향 (2026-11-18)

### 구현 전략

- 코어는 대부분 **Rust**로 작성하며, Rust 코드 레포는 개별 레포 단위로 `apps/`, `crates/` 구조의 모노레포(Cargo 워크스페이스)로 운영합니다(비-Rust 전용 레포는 해당 생태계 구조를 따름).
- 처음부터 전부 새로 만들지 않습니다. **DSL(proc macro, QML/Slint 스타일, Dioxus `rsx!` 등)을 채택하는 이유는 오직 개발 생산성 때문**입니다. 개발 생산성과 가독성이 충족되거나 더 효율적인 방법이 있다면(예: GPUI식 순수 Rust 빌더·체이닝, 코드젠, 트레이트 조합 등) **그 어떤 방법을 사용해도 무관**합니다.
- **웹(DOM)과 네이티브(GPU/CPU) UI는 `lace` 하나로 통합하여 동일한 UI 문법을 사용**하며, 거기에 웹(DOM) 전용 기능이 들어가느냐 네이티브 전용 기능이 들어가느냐에 따라 타깃 기능이 나뉩니다.
- 성능 위주의 검증된 라이브러리·프레임워크를 **포크하거나 기반으로 삼되 (`unit optimization` 적용)**, **수직 통합을 위해 `hyper`의 core를 단일 기준(ref)으로 삼아 구현**하고 **그 위에 호환 어댑터를 두는 구조**로 작업합니다.
- **unit optimization 운영 방식**: 우선 **(1단계) 범용 추상화·미사용 피처를 걷어내고 `hyper` 코어 타입과 무변환·제로카피로 직결하는 수직화**를 기본 적용하며, **(2단계) 병목이 확인된 핫패스에 한해 메모리 레이아웃(Arena/SoA)·SIMD 등 심화 개조**로 확장할 여지를 둡니다. 공통 포크 절차는 [05-development-rules](05-development-rules.md) §7입니다.

### 규약 모델 원칙

- 코어와 내부에서 사용하는 규약 모델은 **표준 준수보다 성능과 수직 통합 시 생산성이 극대화되는 스택**을 씁니다.
- **외부 호환은 개별 어댑터를 구축**하는 방식으로 해결합니다. 내부 규약을 외부 표준에 맞추느라 성능·생산성을 포기하지 않습니다.
- 구체적인 내부 포맷·스택 선택은 아직 결정되지 않았습니다(**미정**, [열린 결정](07-open-questions.md)). 이 원칙은 선택 기준이며 특정 스택의 승인이 아닙니다.
