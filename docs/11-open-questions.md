# 11. 열린 결정 (미정 사항)

> 기준일: 2026-11-16

아직 결정되지 않은 사항의 목록입니다. 각 항목이 결정되면, 결정 내용·날짜·결정자를 기록하고 관련 문서의 상태를 **제안/미정 → 확정**으로 바꿉니다. 이 목록에서 지우지 말고 아래 "결정됨" 절로 옮깁니다.

## 열려 있는 결정

| # | 결정 | 왜 중요한가 | 지금의 방향(제안) |
|---|---|---|---|
| 1 | 엔진 코어 언어·타깃 플랫폼 | 되돌리기 가장 비싼 결정. 성능 목표(물리 시뮬레이션 포함)와 웹 우선 여부에 따라 갈림 | 미정. 웹 우선이면 WebGPU(필요 시 WebGL2 대체)가 축. 코어 언어(Rust + wasm, TypeScript 등)는 성능 목표와 개발 방향에 따라 결정 |
| 2 | 에디터 형태 | 웹 전용이냐 네이티브 앱도냐에 따라 배포·인프라가 달라짐 | 웹 중심이면 Cloudflare 구성과 잘 맞음 |
| 3 | 실시간 공동 편집 도입 시점 | Durable Objects 비용과 복잡도가 큼 | 공유·리믹스 다음 단계로 미룸 |
| 4 | 장면 포맷 | 자체 포맷이냐 glTF 확장이냐. SDK 생태계에 큰 영향 | 미정 |
| 5 | 계정 요구 범위 | 공유·리믹스에는 로그인 필요 | 로그인 없이 로컬 작업만 가능하게 할지 함께 결정 |
| 6 | DS 담당과 범위, 웹 스택 추천 수용 여부 | DS를 혼자 시작할지, 첫 에디터와 함께 키울지 | 토큰+최소 부품만 첫 에디터와 함께. 추천 스택: Astro / Workers+Hono / React+Vite ([아키텍처](05-architecture.md)) |
| 7 | 네이티브 서비스 필요 영역 | 높은 수준의 소켓·이벤트 루프 제어(axum/netpoll급)가 필요한 영역이 실제로 있는지 | 실제 필요가 확인된 영역만 네이티브로 분리하고, 계정·메타데이터·에셋은 Cloudflare 유지 |
| 8 | 룸당 접속 수·초당 메시지 상한 | 통신 규약의 숫자 확정 | 부하 테스트 후 [실시간 통신 규칙](07-realtime-communication.md) §8에 기록 |

## 결정을 기록하는 법

결정이 나면 이 파일의 표에서 "결정됨" 절로 옮기면서 다음을 남깁니다:

```
- 결정: 무엇을 하기로 했는가
- 날짜·결정자
- 이유: 한두 문장
- 영향: 바뀌는 문서/코드
```

규모가 큰 결정은 별도 ADR 문서(`decisions/NNNN-제목.md`)로 남기는 것을 제안합니다.
