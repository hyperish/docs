# 07. 열린 결정 (미정 사항)

> 기준일: 2026-11-17

이 명세 전체에 걸린 미정 사항의 목록입니다. 각 항목이 결정되면 결정 내용·날짜를 기록하고 관련 문서의 상태를 **제안/미정 → 확정**으로 바꿉니다. 이 목록에서 지우지 말고 "결정됨" 절로 옮깁니다.

**경계**: 개별 제품이나 개별 코드 레포 내부의 결정은 이 목록에서 추적하지 않습니다. 해당 제품·레포의 문서가 추적합니다.

## 열려 있는 결정

| # | 결정 | 왜 중요한가 | 지금의 방향(제안) |
|---|---|---|---|
| 1 | unit optimization의 정의와 운영 방식 | 포크 운영 전략의 핵심 절차. 단위·기준·도구가 정해져야 포크 작업을 시작할 수 있음 | 미정. 전략만 언급되었고 구체 설명은 아직 없음 |
| 2 | DSL 문법과 표현 범위 | 프레임워크의 첫인상과 표현력을 결정 | proc macro 기반 선언적 DSL, 컴파일 타임 검증 최대화 ([01-dx-principles](01-dx-principles.md)) |
| 3 | 내부 규약 모델의 구체 스택·포맷 | 성능·수직 통합 생산성 우선 원칙은 확정이지만 무엇을 쓸지는 미정. 코어 설계의 전제 | 미정. 외부 호환은 어댑터로 분리하는 원칙만 확정 |

## 결정됨

- 결정: 코드 레포를 hyper(개발 프레임워크), ring(백엔드), lace(웹), hera(네이티브) 등으로 분리하고, Rust 코드 레포는 개별 레포 단위로 `apps/`, `crates/` 모노레포(Cargo 워크스페이스) 구조를 사용
  - 날짜: 2026-11-16 (모노레포 구조 구체화: 2026-11-17)
  - 영향: docs/00, 05, skills/hyperish-spec
- 결정: docs는 모든 제품이 공유하는 범용 명세만 다루고, 세부 제품·레포 문서는 각 코드 레포에 둠
  - 날짜: 2026-11-16
  - 이유: 세부 제품 문서는 각 레포 소관이며 docs는 그것들을 종합하는 범용 명세
  - 영향: README, docs 전체
- 결정: 코어는 대부분 Rust로 작성
  - 날짜: 2026-11-16
  - 이유: 처음부터 다 깎기에는 공수가 많이 듦
  - 영향: docs/00, 05, 06
- 결정: Rust proc macro로 DSL 제작
  - 날짜: 2026-11-16
  - 영향: docs/01
- 결정: 기존 라이브러리·생태계 코어를 포크한 뒤 unit optimization을 거치는 운영
  - 날짜: 2026-11-16
  - 영향: docs/00, 05. 최적화의 구체적 의미는 열린 결정 #1
- 결정: 코어·내부 규약 모델은 표준보다 성능과 수직 통합 생산성이 극대화되는 스택, 외부 호환은 개별 어댑터
  - 날짜: 2026-11-16
  - 영향: docs/00, 02, 03, 04. 구체 스택은 열린 결정 #3
