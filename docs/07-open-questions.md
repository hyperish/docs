# 07. 열린 결정 (미정 사항)

> 상태: "열려 있는 결정"은 **미정**(방향은 **제안**), "결정됨"은 **확정** 기록(제안으로 추가한 내용은 항목 안에 표시) · 기준일: 2026-11-24

이 명세 전체에 걸린 공통 미정 사항의 목록입니다. 개별 제품이나 개별 코드 레포 내부의 미정 사항은 해당 레포의 `docs/04-open-questions.md`에서 추적합니다. 레포 문서가 확정한 스택 결정은 여기에 색인으로만 남기고, 내용은 그 레포 문서가 소유합니다.

## 결정됨

- **구현 전 명세 보강: 보안 규칙 확정** (2026-11-24)
  - 이유 및 내용: 자격 증명 값은 암호학적 난수로 만들고 식별용 ID를 재사용하지 않음. 응답을 재사용하는 계층(캐시, 멱등 응답 저장소)은 권한 검사 뒤에 두고 재사용 키에 인증 주체를 포함함. 철회는 파생된 갱신 수단까지 폐기함. 실시간 메시지의 중복 제거 범위는 같은 인증 주체의 같은 동기화 단위로 한정함(제안) (`docs/02` §6, `03` §3, §6, `04` §2)
- **Phase 1 완료 기준과 레포별 구현 계획 문서 신설** (2026-11-24)
  - 이유 및 내용: 패밀리 차원의 Phase 1 완료 기준(수직 슬라이스)을 `docs/00`에 확정하고, 각 코드 레포 문서 구조에 `05-implementation-plan`(작업 순서, 완료 기준)을 추가함. 릴리스(공개 크레이트 전부를 같은 버전으로 의존 순서대로 배포, 레포 간 의존은 레지스트리 버전 요구, `Cargo.lock` 커밋)와 품질 규칙(컴파일 실패 테스트, 최소 Rust 버전 CI 검증)을 **제안**으로 추가함 (`docs/00`, `05` §1, §5, §8, 각 레포 `docs/05`)
- **패밀리 네이티브 비동기 런타임 `tokio` 및 외부 의존성 기록 규칙** (2026-11-24)
  - 이유 및 내용: `hyve` 코어 크레이트는 런타임에 의존하지 않고, 네이티브 런타임은 `tokio`(외부 의존성, 포크하지 않음), 웹은 브라우저 이벤트 루프로 확정함. 포크하지 않는 의존성은 허용 라이선스 확인 후 각 레포 포크 표 아래에 기록하며 별도 결정 기록은 필요 없음 (`docs/05` §7, `hyve/docs/02` §2.5, `orbic/docs/02` §3, `04`, `serge/docs/02` §3)
- **`orbic` 포크 단위에 DB 드라이버 크레이트 포함** (2026-11-24)
  - 이유 및 내용: `sqlx-core`만으로는 드라이버가 없어, 같은 저장소의 `sqlx-postgres`·`sqlx-sqlite`를 같은 포크 단위로 포함함 (`orbic/docs/02` §3)
- **`serge` 컴포넌트 인자 규칙 확정 및 확정 예시 정정** (2026-11-24)
  - 이유 및 내용: 컴포넌트 인자의 출처를 주입(`Ctx<T>`), 라우트 파라미터, 부모가 넘기는 프로퍼티 셋으로 한정함. 라우트 진입 컴포넌트가 출처 없는 시그널을 받던 확정 예시를 이 규칙에 맞게 고침 (`serge/docs/01` §1)
- **`serge` GPU → CPU 폴백 정책 확정** (2026-11-24)
  - 이유 및 내용: GPU 디바이스 생성 실패 시 자동 폴백, 환경 변수로 명시 지정, 헤드리스 테스트는 CPU (`serge/docs/04`)
- **`opale` 경계 확정(Phase 1에 영향을 주는 부분만)** (2026-11-24)
  - 이유 및 내용: GPU 기반 크레이트의 포크는 `serge`가 가진 한 벌만 두며 `opale`이 같은 크레이트를 따로 포크하지 않음. `opale`은 Phase 1~3 수직 슬라이스 밖이고, `serge`와는 외부 GPU 텍스처 합성으로 잇는 방향을 유지함. 제품 범위는 미정으로 남김 (`docs/00`, `serge/docs/04` #1)
- **`#[server]` 스텁을 모든 빌드에 두고 전송 계약을 한 곳에 정의** (2026-11-24)
  - 이유 및 내용: 테스트 바이너리는 공유 크레이트를 한 가지 피처 조합으로만 빌드하므로, 스텁이 클라이언트 빌드에만 있으면 포트 없는 풀스택 테스트가 성립하지 않음. 함수 이름으로 부르는 것은 어느 빌드에서나 스텁으로 하고(확정), 핸들러 본문에는 `orbic`의 등록을 거친 요청 파이프라인으로만 닿게 함. 스텁이 전송을 찾는 방법, 고속 레일의 HTTP 운반 형식(미디어 타입, 함수 지정·지문 헤더, 불일치 시 `415 schema_mismatch` 후 표준 레일 폴백), 표준 레일의 오류 복원 규칙은 **제안**으로 `hyve/docs/03` §3에 모음 (`hyve/docs/02` §2.4, `03` §3, `orbic/docs/01` §2, `03` §1, `serge/docs/03` §2.1)
- **오류 봉투에 `requestId` 자리 확정, 프레임워크 오류 코드 추가** (2026-11-24)
  - 이유 및 내용: 봉투 정의에 `requestId` 필드가 없어 두 레일의 오류 복원 규칙과 어긋났음. 모든 오류 응답이 `error.requestId`를 싣도록 하고, 재시도 가능 여부는 `Retry-After` 유무로 전달함. 표에 `405`, `413`, `415`, `422`와 `csrf_token_invalid`, `route_not_found`를 **제안**으로 추가함 (`docs/03` §4, §8)
- **릴리스 순환 해소** (2026-11-24)
  - 이유 및 내용: `v0.1.0`은 세 레포가 모두 끝나야 붙는데 `orbic`·`serge`는 `hyve`의 레지스트리 버전이 있어야 시작할 수 있었음. Phase 구현 중에는 `0.1.0-alpha.N` 프리릴리스로 의존하고, 레포 단위 릴리스와 크레이트 단독 릴리스의 버전 규칙을 구분함. 포크 소스의 배치와 이름, 최소 Rust 버전 값의 기준도 **제안**으로 추가함 (`docs/05` §5, §7, §8)
- **CLI와 프레임워크의 호출 경계** (2026-11-24)
  - 이유 및 내용: 의존 방향이 `orbic`, `serge` → `hyve`라서 `hyve-cli`가 프레임워크 코드를 링크할 수 없음. 각 프레임워크가 `hyve-<프레임워크>` 실행 파일로 자기 단계를 제공하고 `hyve`가 하위 프로세스로 호출함(**제안**) (`hyve/docs/01` §2, `orbic/docs/01` §4, `serge/docs/03` §2.1)
- **미정으로 남긴 항목과 결정 시점** (2026-11-24)
  - 이유 및 내용: Phase 1을 막지 않는 항목은 결정 시점을 적어 미룸 — `opale` 제품 범위(설계 착수 시), `hyve preview` 바이너리 핫패칭(Phase 3 착수 전), `orbic` 엣지 런타임 어댑터(Phase 3 완료 후 또는 요구 발생 시), `serge` 외부 GPU 텍스처 공유 규격(`opale` 설계 착수 시), `serge` → `orbic` 서빙 핸드오프 시그니처(Phase 2 착수 전)

- **문서 충돌 해소 기준 명문화** (2026-11-24)
  - 이유 및 내용: 설계안이 갈리거나 문서가 충돌하면 규약 모델 원칙(핫패스 비용이 적은 쪽, 한 번 선언해 전 계층이 쓰는 쪽)으로 고르되 안전·권한 계약은 예외로 둠. 아래 2026-11-24 항목은 이 기준으로 정리한 결과임 (`README.md`, `docs/00`, `01`)
- **단일 `Signal<T>` 모델 재확인** (2026-11-24)
  - 이유 및 내용: `serge` 문서에 남아 있던 `SyncSignal`·"이원화 시그널" 표기를 `hyve`가 확정한 단일 `Copy` 핸들 `Signal<T>`로 통일함. 스레드 모드는 공개 타입이 아니라 내부 스토리지에서 갈림 (`hyve/docs/02` §2.2, `serge/docs/00`, `03`)
- **Dual-Rail 폴백에서도 고속 레일은 내부 코덱 유지** (2026-11-24)
  - 이유 및 내용: 저지연 전송이 막혀 WebSocket으로 폴백해도 하이퍼리쉬 계층 간에는 내부 바이너리 코덱을 바이너리 프레임으로 유지하고, JSON 텍스트 프레임은 외부 호환용 표준 레일의 규칙으로 한정함. 표준 레일로 내려가는 것은 양쪽의 스키마·코덱 버전이 어긋날 때뿐임(이 폴백 조건은 **제안**). 3-Tier 목록에 섞여 있던 인라인 서버 함수 경계는 별도 항목으로 분리 (`docs/02` §5, `04`, `orbic/docs/00`, `02`, `03`, `serge/docs/03`)
- **Phase 1 의존 폐포 보정** (2026-11-24)
  - 이유 및 내용: Phase 1이 스스로 닫히도록 `hyve-macros`·`hyve-api`·`hyve-parser`·`hyve-diagnostics`, `orbic-macros`·`orbic-cache` 인메모리 저장소, `serge-adapter-client`(Tier 1·Tier 3 요청-응답), `hyve preview`의 기본 실행(상태 보존 HMR은 Phase 2 유지)을 Phase 1에 포함함. 세션 즉시 철회의 확정 내용은 "권위 저장소 직접 조회"이며, L2(Redis/Valkey)는 멀티 레플리카 구성의 권위 저장소로 Phase 2에 추가함 (`hyve`/`orbic`/`serge` `docs/04`)
- **`#[server]` 소유·해석·게이팅 기준 정리** (2026-11-24)
  - 이유 및 내용: 매크로는 `hyve-macros`가 소유하고, 어트리뷰트의 메서드·경로 인자는 `hyve`가 해석하지 않는 바인딩 메타데이터이며 `orbic`만 HTTP 라우트로 해석함. 클라이언트 빌드의 본문 제거 기준은 타깃 아키텍처가 아니라 `server` 피처임 (`hyve/docs/02`, `03`, `orbic/docs/01`)
- **`orbic` 코어와 HTTP 어댑터의 분담 정리** (2026-11-24)
  - 이유 및 내용: 코어 무오염 원칙에 맞춰 CORS·보안 헤더·요청 크기 제한 같은 HTTP 고유 항목은 `orbic-adapter-http`가, 전송 중립 요청 파이프라인은 `orbic-core`가 가지며 모든 어댑터와 `TestClient`가 같은 파이프라인을 호출함 (`docs/02` §5, `orbic/docs/00`, `02`, `03`)
- **`#[server]` 호출 스텁의 인자·오류 전달 규칙 확정** (2026-11-24)
  - 이유 및 내용: 전송 인자는 래퍼 없이 하나의 요청 모델로 보내고(1개면 그 값 자체, 여러 개면 선언 순서대로 묶음), 오류는 종류·코드·재시도 가능 여부·상관관계 ID를 두 레일에서 똑같이 복원함. 고속 레일도 신뢰 경계로 보아 서버 재검증과 내부 세부 비노출을 적용함. 표준 레일에서 인프라 오류를 내부 결함과 구분할 수 있도록 HTTP 규약 표에 `503`을 **제안**으로 추가함 (`docs/03` §4, `hyve/docs/02` §2.4, `orbic/docs/01` §2, `03` §1)
- **`sql!` 오프라인 검증 방식 확정** (2026-11-24)
  - 이유 및 내용: 매크로에 SQL 타입 추론을 다시 구현하지 않고 DB 엔진의 분석 결과를 레포에 커밋한 캐시로 검증함. 컴파일 중에는 DB에 접속하지 않으며, 검증되지 않은 방언에서 실행하면 명시적 오류를 냄 (`orbic/docs/01` §4)
- **포크 표 기록 규칙 및 라이선스 보정** (2026-11-24)
  - 이유 및 내용: 표의 버전은 확인 시점 스냅샷으로 취급하고 출처·확인 날짜를 함께 남김. 포크 금지 대상을 "`MIT`를 단독으로 선택할 수 없는 크레이트"로 일반화해 `slotmap`(`Zlib` 단독)을 포크 대상에서 제외하고, 누락된 라이선스(`rtrb`, `quinn`, `parley`)와 `raw-window-handle` 표기를 보정함 (`docs/05` §7, `hyve`/`orbic`/`serge` `docs/02` §3)
- **범용 명세의 범위 예외 명시 및 `opale` 역할표 등재** (2026-11-24)
  - 이유 및 내용: 이 레포가 레포 고유 이름을 담을 수 있는 곳을 역할표·공유 심볼 이름·결정 색인 세 가지로 한정하고, 스택 내용은 레포 문서가 소유하도록 문구를 맞춤. `opale`은 README 기준 역할만 역할표에 올리고 범위는 미정으로 추적함 (`README.md`, `docs/00`, `02`, `05` §1, §7)

- **전 레포 순수 `MIT` 라이선스 통일 및 포크 라이선스 원칙 확정** (2026-11-19)
  - 이유 및 내용: 하이퍼리쉬 패밀리 전 레포·크레이트를 순수 `MIT` 단일 라이선스로 통일하고, 직접 포크·내부 개조 대상은 `MIT` 선택 가능 크레이트로 제한하며 `Apache-2.0` 단독 크레이트는 외부 의존성/아키텍처 레퍼런스로만 사용함 (`docs/05` §5, §7)
- **내부 바이너리 와이어 포맷(`rkyv`) · MIT 포크 스택 및 내부 코어 `unit optimization` 방향 확정** (2026-11-19)
