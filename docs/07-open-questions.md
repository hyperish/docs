# 07. 열린 결정 (미정 사항)

> 상태: "열려 있는 결정"은 **미정**(방향은 **제안**), "결정됨"은 **확정** 기록(제안으로 추가한 내용은 항목 안에 표시) · 기준일: 2026-11-24

이 명세 전체에 걸린 공통 미정 사항의 목록입니다. 개별 제품이나 개별 코드 레포 내부의 미정 사항은 해당 레포의 `docs/04-open-questions.md`에서 추적합니다. 레포 문서가 확정한 스택 결정은 여기에 색인으로만 남기고, 내용은 그 레포 문서가 소유합니다.

## 열려 있는 결정

| # | 결정 항목 | 왜 중요한가 | 지금의 방향(제안) |
|---|---|---|---|
| 1 | `opale`(그래픽 프레임워크)의 범위와 다른 레포와의 경계 | 역할표에 이름만 있고 설계 문서가 없음. `serge`의 네이티브 GPU 렌더 계층과 GPU 디바이스·기반 크레이트가 겹칠 수 있음 | `opale`에 `docs/00`~`04`를 만들 때 확정. `serge`와는 외부 GPU 텍스처 합성(`serge/docs/04-open-questions.md` #1)으로 잇고, 두 레포가 같은 GPU 기반 크레이트를 따로 포크하지 않게 조율 |

레포별 세부 미정 사항은 각 코드 레포의 `docs/04-open-questions.md`에서 추적합니다.

## 결정됨

- **문서 충돌 해소 기준 명문화** (2026-11-24)
  - 이유 및 내용: 설계안이 갈리거나 문서가 충돌하면 규약 모델 원칙(핫패스 비용이 적은 쪽, 한 번 선언해 전 계층이 쓰는 쪽)으로 고르되 안전·권한 계약은 예외로 둠. 아래 2026-11-24 항목은 이 기준으로 정리한 결과임 (`README.md`, `docs/00`, `01`)
- **단일 `Signal<T>` 모델 재확인** (2026-11-24)
  - 이유 및 내용: `serge` 문서에 남아 있던 `SyncSignal`·"이원화 시그널" 표기를 `hyve`가 확정한 단일 `Copy` 핸들 `Signal<T>`로 통일함. 스레드 모드는 공개 타입이 아니라 내부 스토리지에서 갈림 (`hyve/docs/02` §2.2, `serge/docs/00`, `03`)
- **Dual-Rail 폴백에서도 고속 레일은 내부 코덱 유지** (2026-11-24)
  - 이유 및 내용: 저지연 전송이 막혀 WebSocket으로 폴백해도 하이퍼리쉬 계층 간에는 내부 바이너리 코덱을 바이너리 프레임으로 유지하고, JSON 텍스트 프레임은 외부 호환용 표준 레일의 규칙으로 한정함. 표준 레일로 내려가는 것은 양쪽의 스키마·코덱 버전이 어긋날 때뿐임(이 폴백 조건은 **제안**). 3-Tier 목록에 섞여 있던 인라인 서버 함수 경계는 별도 항목으로 분리 (`docs/02` §5, `04`, `orbic/docs/00`, `02`, `03`, `serge/docs/03`)
- **Phase 1 의존 폐포 보정** (2026-11-24)
  - 이유 및 내용: Phase 1이 스스로 닫히도록 `hyve-macros`·`hyve-api`·`hyve-parser`·`hyve-diagnostics`, `orbic-macros`·`orbic-cache` 인메모리 저장소, `serge-adapter-client`(Tier 1·Tier 3 요청-응답), `hyve preview`의 기본 실행(상태 보존 HMR은 Phase 2 유지)을 Phase 1에 포함함. 세션 즉시 철회의 확정 내용은 "권위 저장소 직접 조회"이며, L2(Redis/Valkey)는 멀티 레플리카 구성의 권위 저장소로 Phase 2에 추가함 (`hyve`/`orbic`/`serge` `docs/04`)
- **`#[server]` 소유·해석·게이팅 기준 정리** (2026-11-24)
  - 이유 및 내용: 매크로는 `hyve-macros`가 소유하고, 어트리뷰트의 메서드·경로 인자는 `hyve`가 해석하지 않는 바인딩 메타데이터이며 `orbic`만 HTTP 라우트로 해석함. 클라이언트 빌드의 본문 제거 기준은 타깃 아키텍처가 아니라 `server` 피처임 (`hyve/docs/02`, `03`, `orbic/docs/01`)
- **`orbic` 코어와 HTTP 어댑터의 분담 정리** (2026-11-24)
  - 이유 및 내용: 코어 무오염 원칙에 맞춰 CORS·보안 헤더·요청 크기 제한 같은 HTTP 고유 항목은 `orbic-adapter-http`가, 전송 중립 요청 파이프라인은 `orbic-core`가 가지며 모든 어댑터와 `TestClient`가 같은 파이프라인을 호출함. `#[server]` 스텁의 인자·오류 전달 규칙은 미정으로 `hyve/docs/04`에서 추적 (`docs/02` §5, `orbic/docs/00`, `02`, `03`)
- **포크 표 기록 규칙 및 라이선스 보정** (2026-11-24)
  - 이유 및 내용: 표의 버전은 확인 시점 스냅샷으로 취급하고 출처·확인 날짜를 함께 남김. 포크 금지 대상을 "`MIT`를 단독으로 선택할 수 없는 크레이트"로 일반화해 `slotmap`(`Zlib` 단독)을 포크 대상에서 제외하고, 누락된 라이선스(`rtrb`, `quinn`, `parley`)와 `raw-window-handle` 표기를 보정함 (`docs/05` §7, `hyve`/`orbic`/`serge` `docs/02` §3)
- **범용 명세의 범위 예외 명시 및 `opale` 역할표 등재** (2026-11-24)
  - 이유 및 내용: 이 레포가 레포 고유 이름을 담을 수 있는 곳을 역할표·공유 심볼 이름·결정 색인 세 가지로 한정하고, 스택 내용은 레포 문서가 소유하도록 문구를 맞춤. `opale`은 README 기준 역할만 역할표에 올리고 범위는 미정으로 추적함 (`README.md`, `docs/00`, `02`, `05` §1, §7)

- **전 레포 순수 `MIT` 라이선스 통일 및 포크 라이선스 원칙 확정** (2026-11-19)
  - 이유 및 내용: 하이퍼리쉬 패밀리 전 레포·크레이트를 순수 `MIT` 단일 라이선스로 통일하고, 직접 포크·내부 개조 대상은 `MIT` 선택 가능 크레이트로 제한하며 `Apache-2.0` 단독 크레이트는 외부 의존성/아키텍처 레퍼런스로만 사용함 (`docs/05` §5, §7)
- **내부 바이너리 와이어 포맷(`rkyv`) · MIT 포크 스택 및 내부 코어 `unit optimization` 방향 확정** (2026-11-19)
  - 이유 및 내용: 내부 제로카피 바이너리 와이어 포맷을 `rkyv`(MIT, `bytecheck` 검증)로 확정하고, 각 코드 레포별 MIT 포크 대상과 1·2단계 내부 코어 개조 타깃(`reactive_graph`, `tachys`, `wgpu`, `taffy`, `sqlx-core`, `fred` 등)을 확정함 (`hyve`/`orbic`/`serge` `docs/02`, `04`)
- **인라인 서버 함수(`#[server]`) ↔ 명시적 컴포넌트 조립 계약 및 풀스택 심볼 분리 확정** (2026-11-19)
  - 이유 및 내용: 숨겨진 전역 자동 등록 대신 `#[server]` 핸들러를 `orbic::component().wrap(...).handle(...)`로 명시 마운트하며, 클라이언트 빌드에서는 `#[server_ctx]` 및 서버 본문을 컴파일 타임에 제거해 클라이언트 스텁만 남김. 풀스택 심볼 충돌 방지를 위해 백엔드 조립은 `orbic::component()`, 프론트 기능 조립은 `serge::feature()`, UI 뷰 함수는 `#[component]`로 고정함 (`docs/02`, `06`, `orbic`/`serge` `docs/01`)
- **패밀리 공통 Phase 1~3 마일스톤 컷(Vertical Slice 우선순위) 확정** (2026-11-19)
  - 이유 및 내용: Phase 1(`v0.1.0` 최소 풀스택·Web DOM·Desktop GPU/CPU 폴백 수직 슬라이스) → Phase 2(`v0.2.0` HMR·캐시·스토리지·잡·SSR/SSG·데스크톱 시스템 API·Shm IPC) → Phase 3(`v0.3.0+` 바이너리 핫패칭·스토어 패키징·WebTransport·MSA·모바일 풀 SDK·SwiftUI/Glance 코드젠)으로 단계적 구현 순서를 확정함 (Phase 1에 들어가는 크레이트 목록은 2026-11-24 보정 기록을 따름)
- **3개 코어 레포·패키지명 crates.io 비충돌 고유명 확정 (`hyper` → `hyve`, `ring` → `orbic`, `lace` → `serge`)** (2026-11-19)
  - 이유 및 내용: crates.io 선점 충돌(`hyper`, `ring`, `lace`)을 근본 해소하고 레포명 = crates.io 패키지명 = Rust 크레이트명 = CLI명을 1:1 일치시키기 위해 3개 핵심 프레임워크명을 `hyve`(올인원 코어·CLI), `orbic`(백엔드), `serge`(크로스플랫폼 UI)로 확정함 (`docs/00`, `01`, `02`, `05`, `06`, `SKILL.md`)
- **3개 코어 레포(`hyve`, `orbic`, `serge`) 분리 및 Rust 모노레포(`apps/`, `crates/`) 구조 확정** (2026-11-16 ~ 2026-11-19)
  - 영향: `docs/00`, `05` (기존 웹/네이티브 UI 레포를 `serge` 단일 레포로 통합)
- **`docs`는 범용 추상 계약만 다루고, 제품·레포별 세부는 각 코드 레포 문서에 위임** (2026-11-16)
  - 영향: `README.md`, `docs` 전체 (`serge` 고유 `ui!` DSL 세부 결정은 `serge/docs/04-open-questions.md`로 이관)
- **Rust 코어 기반 + `hyve` 코어(`ref`) 수직 통합 + 외부/타깃 호환 어댑터 분리** (2026-11-16 ~ 2026-11-17)
  - 영향: `docs/00`, `02`, `03`, `04`, `05`, `06`
- **내부 포크 + 단계적 `unit optimization` 운영 확정** (2026-11-16 ~ 2026-11-17)
  - 이유 및 내용: 1단계(범용 추상화·미사용 피처 제거 및 `hyve` 코어 직결) 기본 적용 후, 병목 구간에 2단계(Arena/SoA·SIMD 등 심화 개조) 여지 확보 (`docs/05` §7)
- **영역별 표현 방식 고정(조립은 Rust 체이닝, UI 뷰 마크업은 proc macro DSL) 및 컴포넌트 기반 아키텍처 고점 개방 확정** (2026-11-16 ~ 2026-11-18)
  - 이유 및 내용: 개발 생산성을 기준으로 `serge`의 UI 뷰 마크업은 **proc macro DSL**로 고정(정적 템플릿 최적화·핫리로드·트리 가독성)하고, 도메인 컴포넌트·라우트·가드 조립(`orbic`, `serge`)은 **순수 Rust 메서드 체이닝**으로 고정함 (`docs/00`, `01`)
- **3-Tier 전송 경계 및 계층별 필수 기본기 범위 확정** (2026-11-18)
  - 이유 및 내용: 인프로세스·로컬 IPC·원격 Dual-Rail 3단계 전송 경계(`docs/02` §5)와 코어·백엔드·웹·네이티브 필수 기본기 범위를 확정함. 레포별 세부 크레이트와 구현 Phase 컷은 각 코드 레포(`hyve`, `orbic`, `serge`)의 `docs/00-overview.md` 및 `04-open-questions.md`에서 관리함
