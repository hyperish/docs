## 결정됨

- 결정: 웹(DOM)과 네이티브(GPU/CPU) UI를 **`lace` 하나로 통합**하여, 프레임워크 패밀리를 **hyper**(개발 프레임워크·툴체인), **ring**(백엔드), **lace**(웹·네이티브 통합 UI) **3개 코어 레포 체제**로 단순화하고, Rust 코드 레포는 개별 레포 단위로 `apps/`, `crates/` 모노레포(Cargo 워크스페이스) 구조를 사용
  - 날짜: 2026-11-16 (모노레포 구조 구체화: 2026-11-17, `lace` 단일 UI 통합: 2026-11-18)
  - 이유: React Native, Flutter, Dioxus처럼 웹과 네이티브가 이미 동일한 UI 문법과 상태(`hyper-state`)를 공유하므로 레포를 분리할 필요 없이 `lace` 안에서 웹(DOM) 타깃과 네이티브(GPU/CPU) 타깃을 함께 제공하는 것이 수직 통합과 DX에 유리함
  - 영향: docs/00, 01, 02, 05, skills/hyperish-spec 및 hyper, ring, lace 문서
- 결정: docs는 모든 제품이 공유하는 범용 명세만 다루고, 세부 제품·레포 문서는 각 코드 레포에 둠
  - 날짜: 2026-11-16
  - 이유: 세부 제품 문서는 각 레포 소관이며 docs는 그것들을 종합하는 범용 명세
  - 영향: README, docs 전체
- 결정: 코어는 대부분 Rust로 작성
  - 날짜: 2026-11-16
  - 이유: 처음부터 다 깎기에는 공수가 많이 듦
  - 영향: docs/00, 05, 06
- 결정: DSL 채택 목적과 표현 수단의 개방성 확정 — DSL(proc macro, QML 기반 Slint, Dioxus `rsx!` 등)을 채택하는 이유는 오직 **개발 생산성** 때문이며, 생산성이 충족되거나 더 효율적인 방법(GPUI식 순수 Rust 빌더, 코드젠 등)이 있다면 어떤 방법을 사용해도 무관함. 단, `lace`의 웹 타깃과 네이티브 타깃은 동일한 UI 문법/표현 체계를 공유함
  - 날짜: 2026-11-16 (원칙 구체화: 2026-11-17)
  - 영향: docs/00, 01 및 전 코드 레포 문서
- 결정: 기존 라이브러리·생태계 코어를 포크한 뒤 unit optimization을 거치는 운영 — 1단계로 불필요한 범용 추상화·미사용 피처를 제거하고 `hyper` 코어(ref)에 직결(수직화)하며, 추후 병목 구간에 한해 2단계(Arena/SoA 메모리 레이아웃·SIMD 등) 심화 개조 여지를 둠
  - 날짜: 2026-11-16 (정의 구체화: 2026-11-17)
  - 영향: docs/00, 05 및 전 레포 문서
- 결정: 코어·내부 규약 모델은 표준보다 성능과 수직 통합 생산성이 극대화되는 스택, 외부 호환은 개별 어댑터
  - 날짜: 2026-11-16
  - 영향: docs/00, 02, 03, 04. 구체 스택은 열린 결정 #2
- 결정: 공통 DX 레퍼런스를 QML/Slint·Dioxus(`rsx!` 및 매크로)·GPUI(순수 Rust 빌더)로 삼고, 모든 레이어는 성능 중심 라이브러리를 포크/기반으로 하되 `hyper`의 core를 단일 기준(ref)으로 수직 통합하고 그 위에 호환 어댑터를 배치
  - 날짜: 2026-11-17
  - 영향: docs/00, 01, 02 및 3개 코드 레포(hyper, ring, lace) 문서
- 결정: 3개 핵심 레포의 세부 도메인과 역할 경계 확정 — `hyper`(기존 Rust/Cargo가 Node.js라면 Bun에 해당하는 올인원 포지션: `init`/`preview`/`lint`/`test`/`build` 통합 툴체인 + 이원화 스레드 모델의 상태성 `signal`·직렬화·파서·**프론트/백엔드 공용 Validation**·공통 UI 문법·**API/OpenAPI 스키마 원천 및 타입 안전 클라이언트 인터페이스** 기본 내장 코어), `ring`(**Rust 스타일 컴포넌트 조립식 백엔드**: DB/ORM 쿼리·Cache·Middleware·Auth·MSA·WS/WT·Swagger 자동 서빙·인메모리 `TestClient` 및 `lace` 프로덕션 서빙 등 백엔드 전반, 레퍼런스 `loco.rs`), `lace`(웹 DOM과 데스크톱·iOS·Android GPU+CPU 폴백 네이티브를 아우르는 **컴포넌트 기반 통합 UI 프레임워크**: 웹 타깃은 Leptos 파이프라인·Ionic형 웹 UI·CRA급 로컬 데브 서빙을 내장하고, 네이티브 타깃은 GPUI·`anomalyco/rune`을 레퍼런스로 자체 WebView를 절대 쓰지 않으며 웹뷰가 필요할 때만 옵트인 웹뷰 어댑터로 웹 타깃 출력을 마운트함)
  - 날짜: 2026-11-17 (`lace` 통합 및 컴포넌트 아키텍처·모듈 분담 확정: 2026-11-18)
  - 영향: docs/00, 01, 02, skills/hyperish-spec 및 각 코드 레포(hyper, ring, lace) 문서
- 결정: 아키텍처 고점 개방 및 문서 UX 원칙 확정 — 프레임워크가 고정된 폴더 구조를 강제하지 않고 개발자가 **Rust 스타일 컴포넌트(Component) 조립**으로 직접 아키텍처를 설계할 수 있게 고점을 높이며, 문서는 Dioxus 0.7 Welcome 가이드처럼 **"왜 써야 하는지(기존 스택 대비 체급 차이), 따라 읽기만 해도 이해되는 프로젝트 구조와 빠른 시작"**이 직관적으로 드러나도록 구성함
  - 날짜: 2026-11-18
  - 영향: docs/01 및 각 코드 레포(hyper, ring, lace) 문서
