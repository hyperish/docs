# 07. 실시간 통신 규칙 (WebSocket)

> 상태: **제안** · 기준일: 2026-11-16

클라이언트-서버 간 실시간 통신의 규약입니다. HTTP API 규약은 [06-api-protocol](06-api-protocol.md)을 따르고, 이 문서는 WebSocket 영역만 다룹니다.

## 1. 용도와 비용도

| 통신 | 프로토콜 |
|---|---|
| 일반 요청/응답 (CRUD, 인증) | HTTPS API ([06](06-api-protocol.md)) |
| 프레즌스(누가 보고 있는가), 공동 편집, 업로드·렌더 진행률 푸시 | WebSocket |
| 큰 데이터 이동 | WebSocket으로 올리지 않음. R2 + API 조합 |

실시간 공동 편집을 첫 버전에 넣을지는 [열린 결정](11-open-questions.md)입니다. 이 규약은 도입 시 따를 기준입니다.

## 2. 연결 수명

1. 클라이언트는 먼저 HTTPS API로 인증하고, WebSocket 연결 URL과 **단기 티켓**을 발급받습니다. 연결 URL에 장기 토큰을 싣지 않습니다.
2. 연결 후 첫 메시지로 `hello`(프로토콜 버전, 클라이언트 정보)를 보냅니다.
3. 서버가 연결을 닫을 때는 표준 close code와 함께 사유를 보냅니다.

## 3. 메시지 규약

- **텍스트 프레임, JSON, UTF-8.** 바이너리 프레임은 쓰지 않습니다(에셋은 R2).
- **클라이언트 → 서버** 메시지:

```json
{ "type": "scene.patch", "id": "01J...", "clientTs": "2026-11-16T01:00:00Z", "payload": { } }
```

| 필드 | 규칙 |
|---|---|
| `type` | `도메인.행위` 소문자, 명령형 (`scene.patch`, `presence.subscribe`). 상세는 [컨벤션](10-naming-conventions.md) |
| `id` | **클라이언트가 생성하는** 메시지 ULID. 요청-응답 대응과 중복 제거에 사용 |
| `clientTs` | 클라이언트 시각. 참고용이며 순서·신뢰의 근거로 쓰지 않음 |
| `payload` | 타입별 본문 |

- **서버 → 클라이언트** 메시지:

```json
{ "type": "scene.patched", "id": "01J...", "seq": 42, "ts": "2026-11-16T01:00:01Z", "payload": { }, "requestId": "01J..." }
```

| 필드 | 규칙 |
|---|---|
| `type` | 서버 통지는 과거형/상태형 (`scene.patched`, `presence.updated`) |
| `seq` | **서버가 부여하는** 룸 단위 단조 증가 시퀀스. 클라이언트는 보낼 때 넣지 않고, 받은 마지막 값을 기억해 재연결 때 사용 |
| `ts` | **서버가 찍는** RFC 3339 UTC |
| `requestId` | 요청에 대한 응답일 때, 클라이언트가 보낸 `id` |

- 실패 응답은 `type: "error"`에 [API 에러 코드 체계](06-api-protocol.md)와 같은 `code` 규칙을 씁니다.

## 4. 룸과 상태 조율

- 조율 단위는 **룸**(프로젝트별, 또는 공유 링크별)입니다. 룸 상태(접속자, 마지막 `seq`)는 **Durable Object**가 담당합니다. Workers만으로는 다중 접속자 상태를 조율할 수 없다는 것이 공식 문서의 안내입니다(2026-11-16 확인: https://developers.cloudflare.com/workers/runtime-apis/websockets/).
- `seq`와 룸 상태는 **Durable Object 스토리지에 영속화**합니다. 메모리에만 두면 휴면·재시작으로 유실되어 재연결 클라이언트의 누락분 복구가 깨집니다.

## 5. heartbeat와 휴면

- 앱 레벨 ping/pong heartbeat는 Durable Object를 주기적으로 깨워 **휴면(hibernation)의 비용 이점을 없앱니다.** hibernation을 쓰는 룸은 주기적 heartbeat를 보내지 않습니다.
- 이 경우 연결 단절 감지는 클라이언트 측 타임아웃과 재연결로 처리하고, 서버는 WebSocket close 이벤트로 프레즌스를 정리합니다.
- hibernation을 쓰지 않는 초기 구현에서는 30초 간격 ping/pong을 쓸 수 있으며, 2회 연속 무응답이면 연결을 닫습니다.

## 6. 재연결과 복구

- 클라이언트는 지수 백오프로 재연결합니다: 1s → 2s → 4s → ... 상한 30s, 매회 지터(±20%).
- 재연결 시 마지막으로 받은 `seq`를 보내 누락분을 다시 받습니다. 서버가 그 시점을 모르면(영속화 범위 밖) 전체 스냅샷으로 재동기화합니다.
- 연결이 끊긴 동안의 사용자 편집은 로컬 큐에 쌓아두고, 복구되면 **원래 `id` 그대로** 순서대로 재전송합니다. 서버는 `id`로 중복을 제거하므로, 이미 처리된 메시지가 다시 와도 부수효과를 반복하지 않습니다(멱등 처리).

## 7. 충돌 (미정)

- 실시간 동시 편집의 도입 자체가 미정입니다. **첫 버전은 한 프로젝트를 소유자 한 명이 한 번에 한 기기에서 편집하는 것으로 제한**해 충돌 자체를 피하는 방향을 제안합니다.
- 그래도 남는 충돌: 같은 사용자의 두 기기, 오프라인 큐 재전송과 서버 상태의 어긋남.
- 단순 LWW(마지막-작성자-승)는 **조용히 데이터를 지울 수 있어 안전한 기본 해법이 아닙니다.** 채택하더라도 손실이 보이게 해야 합니다.
- 제안: 충돌 감지 시 자동 병합하지 않고 사용자에게 선택지(내 변경 유지 / 서버 버전 가져오기 / 사본으로 저장)를 제공합니다.
- 정밀 병합 규칙(LWW, CRDT 등)은 동시 편집을 도입할 때 별도 문서로 결정합니다.

## 8. 제한

- 메시지 하나는 256KB 이하를 원칙으로 합니다. 그 이상은 R2에 올리고 참조를 보냅니다.
- 룸당 접속 수·초당 메시지 수 상한은 부하 테스트 후 숫자를 확정해 이 절에 기록합니다. (미정)
