# 05. 개발 규칙

> 상태: 레포 구성은 **확정**(2026-11-19), 절차 규칙은 **제안** · 기준일: 2026-11-24

하이퍼리쉬 코드 레포들이 따르는 개발 규칙입니다. 이 문서 레포(hyperish/docs)도 이 규칙을 따릅니다. 언어·레포에 공통인 절차 규칙만 다루며, 각 코드 레포의 내부 구조와 세부 절차는 그 레포의 문서가 정합니다. 언어별 컨벤션은 [네이밍·코딩 컨벤션](06-naming-conventions.md)을 봅니다.

## 1. 레포 구성 (확정, 2026-11-19)

- 핵심 프레임워크 코드 레포는 **hyve**(올인원 개발 프레임워크 & 툴체인), **orbic**(백엔드), **serge**(웹·네이티브 통합 UI) 3개로 분리되어 있으며(역할표는 [00-vision](00-vision.md)), **Rust 기반 코드 레포는 개별 레포 단위로 모노레포(Cargo 워크스페이스)** 구성을 따릅니다. 그래픽 프레임워크 **opale**은 스캐폴딩 단계의 레포이며, 범위가 정해지면([07-open-questions](07-open-questions.md)) 같은 규칙과 문서 구조를 따릅니다.
- 대부분의 프로젝트를 Rust로 작성하므로, Rust 코드 레포 내부는 다음과 같이 `apps/`와 `crates/`로 구성합니다(비-Rust 전용 레포는 해당 생태계의 워크스페이스 구조를 따름):

```
apps/        # 실행 가능한 애플리케이션·바이너리·서비스 엔트리
crates/      # 코어 라이브러리, proc-macro DSL, SDK, 내부 포크·최적화 크레이트
```

- 범용 명세는 이 레포(`hyperish/docs`)에 두고, 레포별 세부 설계 문서는 각 코드 레포의 `docs/`에 동일한 구조(`00-overview`, `01-dx-and-dsl`, `02-architecture`, `03-adapters-and-pipeline`, `04-open-questions`)로 둡니다.
- 각 레포와 공개 크레이트는 독립된 버전·독립 태그로 배포합니다.

## 2. 브랜치

- `main`은 항상 배포 가능한 상태로 유지하고 직접 푸시하지 않습니다.
- 작업 브랜치: `feat/…`, `fix/…`, `docs/…`, `refactor/…`, `chore/…` (소문자 kebab-case)
- 브랜치는 하나의 논리적 변경만 담습니다.

## 3. 커밋

- **Conventional Commits**를 씁니다: `타입: 설명`
  - 타입: `feat` `fix` `docs` `refactor` `perf` `test` `chore`
- **한 커밋은 한 논리 변경**입니다. 문서 작업도 문서 단위로 커밋을 나눕니다.
- 커밋 메시지와 코드는 영어/한국어 모두 허용하되 타입 접두어는 영어 소문자로 고정합니다.

## 4. PR과 리뷰

- `main`에 들어가는 변경은 PR을 거칩니다. 혼자 작업할 때도 PR을 열어 변경 이유를 남깁니다.
- PR 설명에는 무엇을/왜 바꿨는지를 적고, 관련 문서를 링크합니다.
- 머지 방식은 변경 성격에 따라 고릅니다. 항목별 이력이 중요한 작업은 개별 커밋을 보존하고, WIP 커밋이 많은 작업은 스쿼시를 쓸 수 있습니다.

## 5. 버전닝과 릴리스 · 라이선스 (MIT 확정, 2026-11-19)

- 하이퍼리쉬 패밀리 전 레포 및 배포 크레이트의 라이선스는 **순수 `MIT` 단일 라이선스**로 통일합니다.
- 배포물은 **Semantic Versioning**(`MAJOR.MINOR.PATCH`)을 씁니다.
- 하위호환을 깨는 변경은 MAJOR를 올리고 CHANGELOG에 기록합니다.
- 배포물은 레지스트리에 버전 태그와 함께 배포합니다. 단일 레포 단위로 릴리스할 때는 `vMAJOR.MINOR.PATCH`, 한 레포 안의 여러 크레이트·패키지를 독립 배포할 때는 `<이름>-vMAJOR.MINOR.PATCH` 태그로 대상을 구분합니다([네이밍·코딩 컨벤션](06-naming-conventions.md) §1).

## 6. 비밀과 환경

- 토큰·키 등 비밀은 절대 커밋하지 않습니다. 환경 변수와 플랫폼의 시크릿 관리 기능으로 관리합니다.
- 비밀이 들어갈 수 있는 로컬 설정 파일은 `.gitignore`에 포함합니다.
- 배포 설정은 코드(설정 파일)로 레포에 둡니다.

## 7. 포크 운영 규칙

기존 라이브러리·생태계 코어를 포크해 쓰는 것은 패밀리 공통의 내부 운영 전략입니다([00-vision](00-vision.md)). 어느 레포에서 운영하든 같은 절차를 따릅니다.

1. **선정**: 포크 대상을 정하고 버전과 라이선스를 확인해 출처·확인 날짜와 함께 기록합니다. **소스를 직접 포크·개조해 우리 MIT 코드베이스에 편입하는 대상은 반드시 `MIT` 단독 또는 `MIT OR Apache-2.0` 등 `MIT` 선택이 가능한 크레이트로 제한**합니다. `MIT`를 단독으로 선택할 수 없는 크레이트(`Apache-2.0` 단독, `Zlib` 단독, `MIT AND …` 결합 등)는 포크하지 않고 외부 의존성(dependency) 또는 아키텍처 레퍼런스로만 활용합니다. 확정되는 것은 베이스 크레이트의 선택이며, 기록한 버전은 확인 시점의 스냅샷입니다. 포크 기준 리비전은 착수 시점에 다시 확인해 고정합니다.
2. **추적**: 업스트림 원본과 우리 변경(패치)을 분리해 추적합니다. 어떤 변경이 우리 것인지 항상 구분할 수 있어야 합니다.
3. **동기화**: 업스트림 업데이트를 가져오는 주기와 충돌 처리 방식을 정합니다.
4. **최적화 (unit optimization)**:
   - **1단계 (기본 수직화)**: 포크 대상에서 불필요한 범용 추상화·미사용 피처/의존성을 제거하고, `hyve` 코어 타입과 무변환·제로카피로 직결합니다.
   - **2단계 (심화 개조 여지)**: 프로파일링·벤치마크에서 병목이 확인된 핫패스에 한해 메모리 레이아웃(Arena/SoA) 개조 및 SIMD 등 저수준 구조 개조로 확장합니다.
5. **검증**: 포크본이 원본과 어떻게 달라졌는지(동작·성능) 측정 결과를 남깁니다.

## 8. 코드 품질 (최소)

- Rust: `rustfmt`와 `clippy`를 통과합니다.
- TypeScript(사용하는 레포): strict 모드, 머지 전 타입 검사와 린트를 통과합니다.
- CI가 생기면 위 검사들을 필수 체크로 둡니다.
