# 09. 개발 규칙

> 상태: 레포 구성은 **확정**(2026-11-16), 절차 규칙은 **제안** · 기준일: 2026-11-16

하이퍼리쉬 코드 레포들이 따르는 개발 규칙입니다. 이 문서 레포(hyperish/docs)도 이 규칙을 따릅니다.

**적용 범위**: 언어·레포에 공통으로 적용되는 절차 규칙을 다룹니다. 언어별 코딩 컨벤션은 [네이밍·코딩 컨벤션](10-naming-conventions.md)을 봅니다.

## 1. 레포 구조 (확정, 2026-11-16)

코드 레포는 4개로 분리되어 있습니다.

| 레포 | 역할 |
|---|---|
| hyper | 개발 프레임워크 |
| ring | 백엔드 |
| lace | 웹 |
| hera | 네이티브 |

- 문서는 이 레포(hyperish/docs)에 둡니다.
- 레포별 세부 구조는 각 레포 문서([02](02-hyper-framework.md) ~ [05](05-hera-native.md))에서 정합니다.
- 각 레포는 독립된 버전·독립 태그로 배포합니다.

## 2. 브랜치

- `main`은 항상 배포 가능한 상태로 유지하고 직접 푸시하지 않습니다.
- 작업 브랜치: `feat/…`, `fix/…`, `docs/…`, `refactor/…`, `chore/…` (소문자 kebab-case)
- 브랜치는 하나의 논리적 변경만 담습니다.

## 3. 커밋

- **Conventional Commits**를 씁니다: `타입: 설명`
  - 타입: `feat` `fix` `docs` `refactor` `perf` `test` `chore`
  - 예: `docs: API 프로토콜 규격 추가`, `feat: DSL 기본 매크로`
- **한 커밋은 한 논리 변경**입니다. 문서 작업도 문서 단위로 커밋을 나눕니다(관계없는 문서를 한 커밋에 섞지 않음).
- 커밋 메시지와 코드는 영어/한국어 모두 허용하되 타입 접두어는 영어 소문자로 고정합니다.

## 4. PR과 리뷰

- `main`에 들어가는 변경은 PR을 거칩니다. 혼자 작업할 때도 PR을 열어 변경 이유를 남깁니다.
- PR 설명에는 무엇을/왜 바꿨는지를 적고, 관련 문서(설계 변경이면 해당 문서)를 링크합니다.
- **머지 방식은 변경 성격에 따라 고릅니다.** 문서·규약처럼 항목별 이력이 중요한 작업은 개별 커밋을 보존(merge commit)하고, WIP 커밋이 많은 기능 작업은 스쿼시를 쓸 수 있습니다.

## 5. 버전닝과 릴리스

- 배포물(프레임워크 SDK, 도구 등)은 **Semantic Versioning**(`MAJOR.MINOR.PATCH`)을 씁니다.
- 하위호환을 깨는 변경은 MAJOR를 올리고 CHANGELOG에 기록합니다.
- SDK는 레지스트리(crates.io 등)에 버전 태그와 함께 배포합니다([비전](00-vision.md)의 배포 방향).

## 6. 비밀과 환경

- 토큰·키 등 비밀은 절대 커밋하지 않습니다. 환경 변수와 각 플랫폼의 시크릿 관리 기능으로 관리합니다.
- `.dev.vars`, `.env`는 `.gitignore`에 포함합니다.
- 인프라 배포 설정은 코드(설정 파일)로 레포에 둡니다.

## 7. 코드 품질 (최소)

- Rust: `rustfmt`와 `clippy`를 통과합니다.
- TypeScript(사용하는 레포): strict 모드, 머지 전 타입 검사와 린트를 통과합니다.
- CI가 생기면 위 검사들을 필수 체크로 둡니다.
