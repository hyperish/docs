# 09. 개발 규칙

> 상태: **제안** · 기준일: 2026-11-16

하이퍼리쉬 코드 레포들이 따르는 개발 규칙입니다. 이 문서 레포(hyperish/docs)도 이 규칙을 따릅니다.

**적용 범위**: 이 문서의 규칙은 TypeScript/JavaScript 기반 웹 서비스 코드(사이트, Workers API, 에디터 셸, DS)와 문서 레포에 적용됩니다. 엔진 코어의 언어는 아직 미정이므로([열린 결정](11-open-questions.md)), 엔진 코드의 규칙은 언어 결정 후 별도 문서로 정합니다.

## 1. 레포 구조

- 제품 코드는 **모노레포**로 시작하는 것을 제안합니다. 구조 제안:

```
apps/        # site(랜딩·문서·갤러리), editor(에디터 앱)
packages/    # engine(SDK), ds(디자인 시스템), api(Workers API), shared(공유 타입·토큰)
```

- 사이트/에디터와 엔진은 **배포 주기가 다르므로 릴리스를 분리**합니다([사이트](03-site.md) 참고). 모노레포 안에서도 엔진 패키지는 독립 버전·독립 태그로 배포하고, 커질 경우 별도 레포로 분리할 수 있음을 열어 둡니다.
- 문서는 이 레포(hyperish/docs)에 둡니다.

## 2. 브랜치

- `main`은 항상 배포 가능한 상태로 유지하고 직접 푸시하지 않습니다.
- 작업 브랜치: `feat/…`, `fix/…`, `docs/…`, `refactor/…`, `chore/…` (소문자 kebab-case)
- 브랜치는 하나의 논리적 변경만 담습니다.

## 3. 커밋

- **Conventional Commits**를 씁니다: `타입: 설명`
  - 타입: `feat` `fix` `docs` `refactor` `perf` `test` `chore`
  - 예: `docs: API 프로토콜 규격 추가`, `feat: 장면 자동 저장`
- **한 커밋은 한 논리 변경**입니다. 문서 작업도 문서 단위로 커밋을 나눕니다(관계없는 문서를 한 커밋에 섞지 않음).
- 커밋 메시지와 코드는 영어/한국어 모두 허용하되 타입 접두어는 영어 소문자로 고정합니다.

## 4. PR과 리뷰

- `main`에 들어가는 변경은 PR을 거칩니다. 혼자 작업할 때도 PR을 열어 변경 이유를 남깁니다.
- PR 설명에는 무엇을/왜 바꿨는지를 적고, 관련 문서(설계 변경이면 해당 문서)를 링크합니다.
- **머지 방식은 변경 성격에 따라 고릅니다.** 문서·규약처럼 항목별 이력이 중요한 작업은 개별 커밋을 보존(merge commit)하고, WIP 커밋이 많은 기능 작업은 스쿼시를 쓸 수 있습니다.

## 5. 버전닝과 릴리스

- 배포물(엔진 SDK, DS 패키지 등)은 **Semantic Versioning**(`MAJOR.MINOR.PATCH`)을 씁니다.
- 하위호환을 깨는 변경은 MAJOR를 올리고 CHANGELOG에 기록합니다.
- SDK는 레지스트리(npm 등)에 버전 태그와 함께 배포합니다([비전](00-vision.md)의 배포 방향).

## 6. 비밀과 환경

- 토큰·키 등 비밀은 절대 커밋하지 않습니다. 환경 변수와 Wrangler 시크릿으로 관리합니다.
- `.dev.vars`, `.env`는 `.gitignore`에 포함합니다.
- Cloudflare 배포 설정은 `wrangler.toml`로 코드에 둡니다.

## 7. 코드 품질 (최소)

- TypeScript strict 모드.
- 머지 전 타입 검사와 린트를 통과합니다. CI가 생기면 이 둘을 필수 체크로 둡니다.
